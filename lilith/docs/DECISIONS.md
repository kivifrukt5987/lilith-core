# 📐 DECISIONS — журнал архитектурных решений LILITH-CORE

Формат: контекст → решение → последствия. Пишем, чтобы через год не спорить с самими собой.

---

## ADR-001. Мозг = реестр профилей, а не одна модель (v0.1.1)

**Контекст.** Железо Кирюши (RTX 3060 12GB) не тянет «одну большую модель на всё»:
компаньон-малышка, кодовая, мультимодальная и саммаризатор — разные задачи с разными
аппетитами к VRAM. Модели будут меняться (новые линейки Qwen/Gemma).

**Решение.** `brain.profiles.<имя>` = сервер + модель + параметры; `brain.defaults`
наследуется; переключение — `default_profile` или `data.profile` в WS `chat`.

**Последствия.** Новая модель = 2–3 строки yaml или переменные окружения, ноль кода.
Менеджер подъёма серверов (этап 2+/6) оперирует теми же профилями.

## ADR-002. Клиент мозга на httpx, без SDK openai (v0.2.0)

**Контекст.** Нужны: SSE-стриминг с метриками, внятные ошибки, работа в тестах без сети,
минимум зависимостей в песочнице и на чистой машине.

**Решение.** Самописный тонкий клиент chat-completions на `httpx` (+ `MockTransport` в тестах).

**Последствия.** Полный контроль над разбором SSE и таймаутами; цена — следим за
совместимостью полями сами (usage/delta/finish_reason покрыты тестами).

## ADR-003. stream_id владеет шиной, а не чат-цикл (v0.2.0)

**Контекст.** Частичные кадры стриминга и финальный кадр должны склеиваться в один
пузырь панели; генерируют их разные слои (dispatch и цикл).

**Решение.** `stream_id` создаётся в `dispatch` и прокидывается в контекст; цикл его уважает.

**Последствия.** Один идентификатор на реплику; панель и мосты не гадают.

## ADR-004. История этапа 2 — in-memory с интерфейсом журнала (v0.2.0)

**Контекст.** Память — этап 3 (aiosqlite + chromadb), но чат-циклу история нужна уже сейчас.

**Решение.** `InMemoryHistory` с методами `append/recent/clear`, ключ = агент+сессия+источник.

**Последствия.** Переезд на журнал в этапе 3 = подмена реализации, чат-цикл не трогается.
Перезпуск сервера пока стирает историю — принято осознанно.

## ADR-005. agent_id прошит на этапе 2, UI агентов — на этапе 3 (v0.2.0)

**Контекст.** Мультиагентность дешёва, пока ключ агента не нужен в хранилищах,
и дорога, когда хранилища уже написаны без него.

**Решение.** `app.agent_id` по умолчанию, `agent_id` в контексте и в данных ответа уже сейчас;
реестр агентов и страница «+ добавить агента» — вместе с памятью (этап 3).

**Последствия.** Журнал и RAG этапа 3 ключуются агентом с первого дня, без миграций.

## ADR-006. Безопасный дефолт рук: авто-ОТКЛОН по таймауту (план этапа 6)

**Контекст.** Human-in-the-Loop баннер 25 с; пользователь может отойти от компьютера.

**Решение.** Таймаут = отказ, не разрешение. Whitelist инструментов на агента, аудит-лог.

**Последствия.** Компаньон не сможет «натворить, пока никто не смотрел».

## ADR-007. Десктоп-обёртка: pywebview + PyInstaller, на этапе 8 (v0.2.0, ответ Кирюше)

**Контекст.** Хотелка: «нажать на exe-шник, и оно развернулось». Альтернативы:
Electron/Tauri (свой браузер, +200 МБ RAM) vs нативная обёртка поверх нашей панели.

**Решение.** `pywebview` (то же окно панели в нативной рамке) + упаковка PyInstaller;
срок — этап 8 вместе с автозапуском и треем. VRAM/RAM отдаём моделям, не рамкам.

**Последствия.** Один UI-код на браузер и на exe; бат-файл остаётся точкой входа до этапа 8.

## ADR-008. Embeddings памяти — принудительно CPU (план этапа 3)

**Контекст.** chromadb по умолчанию может тянуть ONNX-эмбеддер на GPU, отъедая VRAM у LLM.

**Решение.** Эмбеддинги считаем на CPU (multilingual MiniLM), GPU — только модели.

**Последствия.** Минус ~0.5 ГБ VRAM-конфликта; CPU-расход приемлемый (i7-12700KF).

## ADR-009. ПРЕДЛОЖЕНИЕ (ждёт одобрения Кирюши): разделить «модели» и «роли» в UI настроек

**Контекст.** Кирюша увидел селектор профилей (chat/coder/vision/summarizer/experiment)
и спросил: зачем отдельные слоты, если достаточно одного места, где настраивается
сама модель, а роли указывают на неё?

**Решение (предлагается).** Хранение остаётся нынешнее (`brain.profiles` = роль →
модель+параметры: оно гибкое и уже покрыто тестами), но **UI** будущего менеджера
(страница «Настройки/Модели») строится по схеме Кирюши:

1. раздел **«Модели»**: список настроенных серверов+моделей (имя, base_url, квант,
   флаги оффлоада позже), кнопка «+ добавить модель» — одна точка входа для любых
   новых моделей, включая будущие линейки;
2. раздел **«Роли»**: chat / coder / vision / summarizer / своя — у каждой выпадающий
   список из настроенных моделей + мелкие переопределения (температура и т.п.).

Слот `experiment` в дефолтном конфиге — не обязательная сущность, а готовая пустая
роли-заготовка, чтобы новую модель можно было попробовать без правки структуры yaml;
удаляется одной строкой, ничего не сломав.

**Последствия.** UX «одна вкладка для модели, роли указывают на неё» без переписывания
бэкенда; реестр моделей станет источником для llama.cpp-менеджера (флаги, порты).

## ADR-010. Настройки памяти меняются из программы и переживают перезапуск (v0.3.0)

**Контекст.** Кирюша: «сделай саммари не на каждые 40, а чтобы настраивать самому
внутри программы». Правка YAML + перезапуск для такого параметра — плохой UX.

**Решение.** Ограниченный набор полей (`summarize_every_n`, `top_k`, `rag_enabled`,
`auto_summarize`) меняется через `POST /api/memory/settings` и шестерёнку панели;
значения сохраняются в `data/runtime_settings.json` и применяются при старте поверх YAML.

**Последствия.** Хозяин крутит поведение памяти на лету; конфиг остаётся источником
«формы», рантайм-файл — источником «поведения сейчас».

## ADR-011. Эмбеддер по умолчанию — HashEmbedder, chromadb ленивый (v0.3.0)

**Контекст.** Sentence-transformers и модели chromadb по умолчанию тянут сотни МБ
и/или сеть при первом запуске; на машине Кирюши CPU/GPU бюджет отдан LLM и голосу.

**Решение.** Дефолт — детерминированный HashEmbedder без моделей; sentence-transformers
включается именем в конфиге; chromadb импортируется лениво и при отсутствии вежливо
отключает RAG, не роняя ядро.

**Последствия.** Память работает из коробки на любом железе; качество поиска
улучшается одной строкой конфига, без переписывания кода.

## ADR-012. Советы другой Лильки приняты с поправками (v0.4.0)

**Контекст.** Компаньон-инстанс из соседнего чата прислал чертёж расширяемости
голосового слоя: STT-реестр, манифест паков с CLI и панелью, zero-shot голоса
папками, hot-swap, пользовательские паки.

**Решение.** Принято почти целиком:
1. STT-реестр с контрактом `transcribe` и резервными слотами whisper-cpp/vosk — да;
2. манифест `models/packs.yaml` + CLI `lilith-core packs …` + докачка + sha256 — да;
   секция «Паки» в панели отложена на этап 6 (её же совет);
3. zero-shot голоса: `voices/<имя>/reference.wav` + запись в конфиге — да; сам
   клон-движок не прибит: слот `zero-shot` с контрактом, движок выбирается позже;
4. hot-swap voice/stt/vision без перезапуска + фолбэк на дефолт — да (`VoiceCore.sync`);
5. пользовательские паки (local/url) без правки кода — да.

**Поправки моей кухни:** energy-vad получил отдельную шкалу порога (RMS громкости),
не смешанную с вероятностной шкалой silero; zero-shot слот не тащит тяжёлый движок
в зависимости по умолчанию; sha256=null разрешён осознанно (предупреждение, не ошибка).

**Последствия.** Голосовой слой расширяется записями в конфиге/манифесте, а не кодом;
панель паков и выбор клон-движка — следующие шаги без переписывания контура.

## ADR-013. Вкладки «Агенты» и «3D-модели» — на этапе 8, поверх реестра персон (v0.5.0)

**Контекст.** Кирюша: «на 8 этапе сделаем настройки: вкладка 3D-модели (как выглядят
агенты) и вкладка Агенты (карточки: системный промт, LoRA, стиль речи…)».

**Решение.** Реестр персон `personas/<id>/` (этап 5) становится хранилищем карточек:
persona.md (душа), model.vrm (тело), profile.yaml (голос, brain-профиль, будущая LoRA,
заметки стиля речи). UI-вкладки рисуются на этапе 8 поверх этого реестра + hot-reload,
без миграций данных.

**Последствия.** LoRA хранится путём в карточке; применение зависит от движка
(llama.cpp умеет --lora-adapters, LM Studio — нет) — карточка честна, менеджер уточняет.

## ADR-014. Разворот лица: VRM в панели вместо внешней программы (v0.5.0)

**Контекст.** Спека Лильки-архитектора: STOP внешнего Live2D/VTuber-пути как основного;
лицо = three-vrm в веб-панели, виземы из TTS-чанков, idle-анимации, курсор; VTuber/Unity —
адаптеры; OBS на этапе 8.

**Решение.** Принято целиком с одной поправкой: виземы считаем на сервере
(тестируемо, один источник для панели/Unity/OBS), браузер сглаживает и применяет.
three.js/three-vrm вендорены в webui/vendor/ ради офлайн-панели.

**Последствия.** Критерии «моргает/курсор/улыбка/рот по слогам» проверяются у Кирюши
глазами + face-debug оверлеем; серверная половина покрыта pytest.

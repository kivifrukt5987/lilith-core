|---|---|---|

## 3. РАЗБОР НЕЙРОНЫ v2 (докладка с последних кадров) — текст Лильки-архитектора

### 3.1 Транспорт аудио (подтверждено)

FastAPI `:8000`, WS `/api/ms/producer`; чанки **2048 Б** в Unity **Queue Processor** → `AudioSource`.

Консоль:
```
Chunk #80: 99328 samples (2252.3ms)
Buffer: 505856 samples (11470.7ms)
```
→ плебек-буфер **44.1 кГц** (дефолт Unity), XTTS 24k **ресемплится на плебек**.

> **Наша сверка.** Совпадение с нашим контрактом почти полное: тот же FastAPI, тот же
> размер чанка 2048 Б, та же связка «очередь → AudioSource». Отличие одно, но важное:
> у них плебек идёт на 44.1 кГц (дефолт Unity), а 24 кГц XTTS ресемплится **в плебек**;
> у нас (решение A2) сервер приводит поток к 24 кГц, а `AudioClip` создаётся на тех же
> 24 кГц — ресемплинга в Unity нет вообще. Наш путь дешевле по CPU и не вносит
> артефактов, но **вопрос к архитектору** (§6, Q1): не поднять ли `producer_sample_rate`
> до 48000, чтобы избежать рассинхрона с дефолтным `AudioSettings.outputSampleRate`
> на машинах, где Unity насильно ресемплит вывод.

### 3.2 Рот (подтверждено)

**SALSA LipSync** (Crazy Minnow Studio), `Viseme Configuration count=4`: **A / I / E(+preview)**,
триггеры `0.000 / 0.010 / 0.020 / 0.030`.

Компонент **Shape** → `SkinnedMeshRenderer "Body"`, `BlendShape Index` — **японские имена**
(`"え"`), Min 0 / Max 100, timings **On 0.08 / Off 0.06**, Easing **Cubic Out**.

Синхрон: `[BlendShapes] Queued 2 shapes at buffer pos N` — **очередь визем по позиции
аудио-буфера в сэмплах (sample-accurate)**.

> **Наша сверка.** SALSA — платный ассет ([доки Crazy Minnow Studio](https://crazyminnowstudio.com/docs/salsa-lip-sync/modules/salsa/using/),
> анализ аудио в реальном времени), берём **только приёмы**, не продукт:
> 1. **sample-accurate очередь визем** — у нас виземы применяются «по мере анализа окна»,
>    то есть привязаны к тактикам `Update()`, а не к позиции в буфере. Их подход точнее.
>    → **ADR-020 (1)**: добавляем опцией в `AudioQueueProcessor`.
> 2. **Японские имена блендшейпов** (`あ/い/う/え/お`) — так подписаны морфы у многих
>    VRoid-моделей, наш `FaceRig` их сейчас не понимает. → **ADR-020 (2)**: fallback-маппинг.
> 3. **4 виземы вместо 5** (A/I/E + preview) — SALSA сама упрощает; у нас 5 корзин
>    (A/I/U/E/O) как на сервере, оставляем.
> 4. **Timings On 0.08 / Off 0.06 + Cubic Out** — их сглаживание асимметрично: открытие
>    медленнее закрытия. У нас один `visemeSmoothing` на оба направления.
>    → в ADR-020 не заведено (мелочь), но в `VisemeDriver` это можно повторить позже.

### 3.3 Лицо/риг (подтверждено)

**Unity 6.1 (6000.1.9f1)**, OpenGL 4.5; меню **UniGLTF/VRM1** = пакеты VRM 1.0;
иерархия `Root/Face/Body/Hair/secondary` + `DontDestroyOnLoad`.

«День 1»: первое тело — **другая модель (рыжая)**, своп тела посреди разработки
**без поломки пайплайна**.

> **Наша сверка.**
> * `6000.1.9f1` — это **Unity 6.1, tech stream**, а не LTS ([архив релизов Unity](https://unity.com/releases/editor/archive)).
>   Мы по решению **C2** целимся в **6000.0.x LTS**. Клиент не использует ни одного
>   API, появившегося только в 6.1, поэтому соберётся на обеих; расхождение зафиксировано
>   в `unity-client/…/README.md` → **вопрос Q2** (§6).
> * `OpenGL 4.5` — у нас в рекомендациях DirectX11 по умолчанию; для прозрачного окна
>   через DWM разницы нет, но для старых драйверов OpenGL стабильнее. Помечено в README.
> * Иерархия `Root/Face/Body/Hair/secondary` — это **структура VRM-модели**, а не сцены;
>   у нас после `Vrm10.LoadBytesAsync` получается тот же набор узлов. `secondary` —
>   пружинные кости (UniVRM обрабатывает сам).
> * `DontDestroyOnLoad` — у нас клиент живёт в единственной сцене, не требуется;
>   если появится сцена-заглушка/меню, добавим.
> * **«День 1»: своп тела без поломки пайплайна** — ровно то, что мы заложили в
>   `VrmLoader.Swap()` + generation-счётчик (гонка свопов) и в реестр персон. Подтверждено.

### 3.4 Голос (подтверждено)

**Coqui XTTS v2**, cuda; клон: `gpt_cond_latent` + `speaker_embedding` от reference wav;
`temperature=0.8`, `speed=1`.

Стриминг: `wav → чанки по blocksize`, хвост `np.pad`, `stream.write(chunk)` —
**звук играет во время генерации**.

«Новый синтез» добавил **nonverbal**: смех, вздох, хмыканье, крик (теги в стиле Bark;
старый синтез — хрип).

> **Наша сверка.** Наш zero-shot слот (`ZeroShotTTS`, `voices/<имя>/reference.wav`)
> спроектирован ровно под XTTS/IndexTTS/CosyVoice/F5 — контракт уже зафиксирован в
> `voice/tts.py`. Стриминг «звук играет во время генерации» у нас есть:
> `split_sentences()` + `stream()` по предложениям. Отличие: у них чанки по `blocksize`
> внутри предложения (ещё мельче), у нас — по предложениям.
> **nonverbal** (смех/вздох/хмыканье) — у нас такого нет. → **ADR-020 (3)**: слот
> `nonverbal` в `voice.yaml`, реализация **отложена до этапа голоса**.

### 3.5 Мозг/память (ранее)

Облачный **OpenAI** + **SummaryMemory**; **Postgres + Qdrant** в docker;
уши — **NVIDIA Riva** (глава про ASR).

> **Наша сверка.** Осознанно не повторяем: мозг у нас локальный/OpenAI-совместимый
> (реестр профилей, ADR-001), память — **sqlite + chromadb** (этап 3), уши —
> **faster-whisper + silero/energy VAD** (этап 4). Их SummaryMemory концептуально
> совпадает с нашим саммаризатором (`memory/summarizer.py`, порог `summarize_every_n`).

### 3.6 Агентный слой / кодинг (НОВОЕ)

task-сервис `127.0.0.1:8000/tasks/<id>`; пайплайн
`ToolSearch #1 → tool_result → Write #3 → tool_result → text → system`;
`cost_usd ≈ 0.093`, `duration_ms ≈ 27848`, `num_turns 3`.

Внутри **Claude Code + SpecKit**:
```

                  и писал код в изолированной среде"
```

Спеки с **user stories Given/When/Then** и приоритетами **P1–P3**:

| **US3** | сессионные пермишены: allowed tools, таймауты, лимиты ресурсов, пермишены кодинг-агента |
| **US4** | стриминг прогресса и real-time output |

Конституция проекта `.specify/memory/constitution.md` — **4 принципа**:
1. Code Quality First
2. **Testing NON-NEGOTIABLE**
3. UX Consistency
4. Performance: 2 s page load / 200 ms p95

Плюс **Quality Gates** (6-gate merge checklist), **Workflow** (7 шагов), семантическое
версионирование конституции, поправки = письменный proposal + review + инкремент версии.

### 3.7 Инструменты (НОВОЕ)

Инструмент = **маленький сервис**: `calc_service.py` со словарями `OPERATIONS /

## 4. ПОВТОРЯЕМ / НЕ ПОВТОРЯЕМ (ответы архитектора на мои четыре вопроса)

### Повторяем

* чанковость аудио по WS;
* клон от reference wav;
* взгляд через LookAt-аналог;
* **очередь визем по позиции буфера (sample-accurate)** — **ОПЦИЕЙ** в `AudioQueueProcessor`
  (`offset_ms` остаётся дефолтом);
* **четыре виземы с японскими именами блендшейпов** — fallback-маппинг;
* **nonverbal-события** — слот в `voice.yaml` (отложить до этапа голоса);
* **Given/When/Then** приёмочные сценарии в спеках этапов;
* **изолированный воркспейс + cleanup и сессионные пермишены** (whitelist инструментов,
  таймауты, лимиты ресурсов) — в спеку этапа 7 «Руки»;
* стриминг прогресса (**у нас уже есть**: probe/stats).

### Не повторяем

* **SALSA** (платный ассет) — у нас свой `VisemeDriver`;
* **облачный мозг OpenAI** — мы локальные;
* **Postgres + Qdrant** — у нас sqlite + chroma;
* **Riva** — у нас faster-whisper + VAD;
* **Claude Code / SpecKit как продукты** — у нас свой поток
  (`ARCHITECTURE.md` + `DECISIONS.md`/ADR + STAGE-отчёты), **но принцип конституции
  принят: наш `DECISIONS.md` и есть наша конституция**.

## 6. Вопросы к архитектору — ОТВЕЧЕНЫ (22.09.2026) → ADR-021

| # | Вопрос | Решение архитектора | Исполнение |
|---|---|---|---|
| **Q1** | Частота плебека: 24 kHz без ресемплинга или 44.1/48 как у «Нейроны»? | **Держим 24 kHz нативно.** `AudioClip` создаётся с `frequency 24000`, без ресемпла; sample-accurate очередь считает сэмплы в частоте клипа. «Нейронины 44.1 — дефолт их плеера, не доктрина» | ✅ уже так и есть: `AudioClip.Create("LilithVoice", cap, 1, _sampleRate, false)`, `_sampleRate` из `hello` (24000); `PlayPositionSamples`/`EnqueuedSamples` — в сэмплах клипа. Изменений не потребовало |
| **Q2** | Unity 6000.0.x LTS или 6.1 tech stream вслед за референсом? | **6000.0.x LTS.** У Кирюши стоит **6000.0.84f1**. За «Нейрониной» 6.1 не гонимся | ✅ фиксируем в `unity-client/…/README.md`; API 6.1 не используется |
| **Q3** | Асимметричное сглаживание визем (SALSA On 0.08 / Off 0.06 / Cubic Out)? | **Да, взять дефолтом** для локальных визем; серверная очередь под флагом остаётся sample-accurate | ✅ v0.6.2: `LilithClientConfig.visemeOnSeconds=0.08`, `visemeOffSeconds=0.06`, `visemeCubicOut=true`; `VisemeDriver.OpenSeconds/CloseSeconds/CubicOut` + `Approach()`; `EvaluateCubicOut()` — static, тестируема без сцены. Прежний `visemeSmoothing` остался фолбэком (если On/Off = 0) |
| **Q4** | Судьба VMC-моста | **Оставить опциональным внешним адаптером под флагом**, в этапе 7 не развивать, в доках помечать **legacy** | ✅ `face/vtuber_bridge.py` помечен legacy в `ARCHITECTURE.md` §9.8 и в докстринге модуля; `vmc_enabled: false` в конфиге; в план этапа 7 не входит |
| **Q5** | Размер окна под OBS | **512×640 (портрет 4:5)**, borderless + topmost + dockBottomRight; размеры из `face.yaml (window.width/height)`; приёмка — скриншот F7 | ✅ v0.6.2: `WindowSpec` в `PersonaFace`, `face.yaml: window{width,height}`, доезжает в кадре `persona.face.window`; клиент применяет через `ApplyPersonaWindow()` → `TransparentWindow.ApplyWindowSize()` (реальный `SetWindowPos`); дефолт конфига 512×640 |

**Решено заранее (её же словами):** sandbox этапа 7 — **ТОЛЬКО директорией**
(sandbox-dir + confine + cleanup), Docker — опциональный бэкенд позже:
«Кирюша докер выселил из логова, кхххх». Внесено в `docs/STAGE7_HANDS_SPEC.md` §5 Q1.

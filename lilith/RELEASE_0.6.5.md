## 1. Причина моя — и их две, независимые

### №1 Дедлок главного потока (главная, объясняет 100 % симптома)

В 0.6.3 я лечила `CS4032` («`await` в корутине») паттерном «Task внутри корутины»:

```csharp
yield return loadTask;          // ← вот здесь ошибка
if (loadTask.IsFaulted)  { … }
if (loadTask.IsCanceled) { … }
instance = loadTask.Result;     // ← блокировка главного потока
```

Я исходила из того, что «Unity умеет ждать Task в корутине». **Не умеет.**
Unity 6000.0 Manual, «Write and run coroutines», перечисляет, что можно ждать:
`null`, кастомные yield-инструкции, `AsyncOperation`, `Coroutine` и `Awaitable`;
про generic `Awaitable<T>` сказано прямо — **«It's not supported to `yield return`
the generic `Awaitable<T0>` from a coroutine»**. `Task` в списке нет: незнакомый
объект трактуется как «один кадр», и корутина идёт дальше.

Дальше — цепочка, которая не может разорваться:

1. `loadTask.IsFaulted` / `IsCanceled` у **незавершённой** задачи = `false` (исключения нет);
2. `instance = loadTask.Result;` → `.Result` у незавершённой задачи **блокирует вызвавший поток**;
3. продолжения UniVRM при `RuntimeOnlyAwaitCaller` планируются **тем же главным потоком**:
   `NextFrame()` → `NextFrameTaskScheduler.Enqueue(...)` → `UnityLoopTaskScheduler.Instance.Scheduler`
   → `private void Update()` этого MonoBehaviour (сверено по исходникам
   `Packages/UniGLTF/Runtime/Utils/AwaitCaller/NextFrameTaskScheduler.cs`, v0.131.2);
4. главный поток заблокирован → `Update()` не вызывается → очередь не разбирается →
   задача не завершается → `.Result` не возвращается. **Дедлок навсегда.**

Это ровно наблюдаемая картина: последняя строка `старт свопа` (дальше логов нет,
потому что их уже некому печатать), оверлей застыл на «тело грузится…» (`Loading`
не сброшен), редактор не отвечает и снимается только диспетчером задач, 2/2.

**Почему гвард 0.6.3 меня не спас.** Гвард `assert "yield return loadTask;" in text`
держал конструкцию, а не поведение — и конструкция опиралась на недокументированное
поведение движка. Гвард на ложную инвариантность хуже отсутствия гварда: он создаёт
ощущение проверки. В 0.6.5 гвард **перевёрнут** (`yield return loadTask` запрещён),
а рядом с ним — ссылка на документацию Unity и исходники UniVRM.

**Что в гипотезе архитектора совпало и что уточнилось.** Совпало: «виснут внутри
загрузки после "старт свопа"», «зона, не покрытая песочницей». Уточнение: это не
busy-wait и не sync-контекст в Editor'е как таковой — это блокировка главного потока
на `.Result` при том, что планировщик кадров живёт на нём же. Editor здесь не
особый случай: в билде (Build And Run) дедлок был бы **тот же**, просто окно
повисло бы без редактора. То есть баг не «редакторный», а общий — и тем важнее,
что он пойман до билда.

### №2 Процедурная модель была битой (второй блокер, независимый)

Кирюша грузит `tests/samples/test_cube.vrm` — наш процедурный куб (ADR-017).
Проверка по спеке glTF 2.0 (побайтово, в песочнице):

```
acc | type   | comp  | count | bv.len | нужно | влезает
  3 | VEC4   | USHORT|   24  |     48 |   192 | False   <<< JOINTS_0 меша Face
 19 | VEC4   | USHORT|   24  |     48 |   192 | False   <<< JOINTS_0 меша Body
```

`make_test_vrm.py` писал `JOINTS_0` **одним** `uint16` на вершину
(`[bone_index] * count`), а объявлял `VEC4` — нужно четыре. Аксессор выходил за
пределы своего bufferView, и UniVRM читал за границей вьюхи: мусорные индексы
костей до 65535 при 55 суставах. `validate()` этого не проверял — он смотрел
magic, чанки, `VRMC_vrm`, число костей и экспрессий, но **не геометрию данных**.

То есть даже после лечения дедлока загрузка куба не была бы чистой. Порядок
срабатывания в F7: дедлок случается раньше (`.Result` — сразу после создания
задачи), поэтому про модель мы бы узнали следующим замером.

## 2. Что сделано

### 2.1 Лечение №1 — главный поток больше не блокируется никогда

```csharp
var waitStarted = Time.realtimeSinceStartup;
var waitFrames = 0;
var nextReport = 0.5f;
while (!loadTask.IsCompleted)
{
    yield return null;                       // кадр Unity: player loop тикает → планировщик UniVRM работает
    waitFrames++;
    var waited = Time.realtimeSinceStartup - waitStarted;
    if (waited >= nextReport) { nextReport += 0.5f; Debug.Log($"[Lilith] тело: фаза 4 — ждём LoadBytesAsync: {waited:F1} с, {waitFrames} кадров (главный поток не блокирован)"); }
    if (loadTimeoutSeconds > 0f && waited >= loadTimeoutSeconds) { … Debug.LogError(ОТКАЗ) …; Failed?.Invoke(…); yield break; }
}
Debug.Log($"[Lilith] тело: фаза 5 — задача завершена: {waitFrames} кадров, … мс");
…
instance = loadTask.Result;                    // безопасно: IsCompleted гарантирован циклом
```

Четыре вещи, которые тут важны, а не «для красоты»:

* **`yield return null` вместо `yield return task`** — ожидание по кадру, главный поток свободен, планировщик UniVRM получает свои `Update()`.
* **`.Result` только после `IsCompleted`** — блокировка невозможна по построению; гвард проверяет порядок в файле.
* **`loadTimeoutSeconds` (60 с, `0` = вечно)** — зависание превращается в красный `ОТКАЗ` с советом, а не в мёртвый редактор. Продолжение принципов 0.4.1 («окно не умеет умирать молча») и 0.6.3 («исключения достаём явно»): теперь и **зависание** не умеет быть тихим.
* **`Time.realtimeSinceStartup`, а не `deltaTime`** — при подвисании кадров и `timeScale = 0` deltaTime врёт.

Прогресс-лог — раз в 0.5 с (не каждый кадр, иначе Console тонет на тяжёлом теле).

### 2.3 Диагностические флаги (оба — из инспектора `VrmLoader`)

* **`Use Immediate Await Caller`** (дефолт ❌) — `UniGLTF.ImmediateCaller` вместо
  `RuntimeOnlyAwaitCaller`. Сверено по исходникам v0.131.2
  (`Packages/UniGLTF/Runtime/Utils/AwaitCaller/ImmediateCaller.cs`:
  `public sealed class ImmediateCaller : IAwaitCaller`, «синхронное исполнение» —
  `NextFrame`/`Run`/`Run<T>` возвращают уже завершённые Task). С ним next-frame
  планировщик не участвует вовсе → дедлок невозможен конструктивно. Цена: вся
  загрузка в одном кадре, на 20+ МБ это длинный кадр (похоже на подвисание, но
  конечное). В дефолте выключен.
* **`Load From Server Only`** (дефолт ❌) — форсирует HTTP-ветку, игнорируя
  `face.vrm_path` из кадра persona (просилка архитектора).
* **`Load Timeout Seconds`** (дефолт 60, `0` = вечно).

### 2.4 Лечение №2 — модель и её валидатор

* `make_test_vrm.py`: `JOINTS_0` теперь `[bone_index, 0, 0, 0] * vertex_count` —
  четыре `uint16` на вершину, пара к `WEIGHTS_0 = [1, 0, 0, 0]` (первый сустав
  держит весь вес). Оба меша (Face и Body).
* `validate()` усилен новой `_validate_buffers()`: `buffers[0].byteLength == BIN-чанк`;
  каждый bufferView в пределах чанка и ненулевой; **каждый accessor влезает в свой
  bufferView** (`size(componentType) × count(type) × count`); атрибуты одного
  примитива согласованы по `count`, морф-таргеты — тоже.
* `tests/samples/test_cube.vrm` пересобран: **21 480 Б** (было 21 192; +288 = 2 × 144),
  22 accessor'а, все в границах. Старый файл новую проверку **не проходит** —
  это контрольный выстрел по валидатору:
  `accessor[3] (VEC4, componentType 5123, count 24) требует 192 Б, а bufferView[3] вмещает 48 Б`.

### 2.5 Про предложенный обход Кирюши — важная поправка

Эксперимент «кубик копией в `personas/lilith/model.vrm` + закомментировать
`vrm_path` + рестарт сервера → кадр придёт с `face.vrm_path=None` → ветка HTTP»
**не различает причины**: сервер отдаёт по HTTP тот же самый файл
(`tests/samples/test_cube.vrm`), то есть байты в `Vrm10.LoadBytesAsync` попадут
идентичные. Ветвление file/HTTP заканчивается на строке `bytes = …`, дальше код
один и тот же. Поэтому:

* если виснет в обеих ветках — это ничего не доказывает (дедлок ветко-независим, так и есть);
* «если грузится — виновата file-ветка» — вывод, который из этого эксперимента
  получить нельзя.

**Решающие A/B вместо него** (оба — без правки кода, флагами из инспектора):

| A/B | Что различает |
|---|---|
| `Use Immediate Await Caller` ❌ → ✅ | планировщик кадров vs всё остальное. Если с ✅ грузится, а с ❌ фаза 4 идёт вечно — виноват next-frame планировщик |
| `test_cube.vrm` → настоящая VRoid-модель | байты модели vs загрузчик. Если на настоящей модели грузится, а на кубе нет — дело было в модели (до 0.6.5 — вполне вероятный сценарий) |

Оба эксперимента Кирюша может провести за минуту каждый, и оба дают однозначный
ответ в логе (фаза 2 печатает, какой caller применён).

### 2.6 Печать вторая: замер Б/В — точка зависания плавает внутри рукопожатия

После первой печати архитектор прислала **три подписи одного бага**:

| Замер | Конфиг | Последняя строка в Console |
|---|---|---|
| А (23:14) | `vrm_path` → файл | `тело: старт свопа 'lilith' ← файл …` |
| Б (23:27) | то же | `тело: прошу у сервера кадр персоны 'lilith' (persona_request, hello)` |
| В (23:53) | чистый HTTP (`vrm_path` закомментирован, `model.vrm` рядом, проба 13/13) | та же первая строка, **загрузка не начиналась вовсе** |

Вывод архитектора верный: точка замера плавает внутри рукопожатного залпа
(`hello`×2, `state`×2, `persona`, `focus`) → это **не** ветка загрузки. И главное
для меня: в Б/В своп не стартовал, значит **мой `.Result`-дедлок их не объясняет** —
он срабатывает позже. Лечение №1 было необходимым, но не достаточным.

Чтение транспорта (Unity в песочнице нет, поэтому — по коду) дало три находки,
каждая из которых способна остановить главный поток:

1. **`LilithWSClient.DisconnectInternal()`: `CloseAsync(...).Wait(TimeSpan.FromSeconds(1))`.**
   Блокировка вызывающего потока, а вызывается это с главного (`Connect()`/`Disconnect()`/
   `OnDestroy`). Ждать close-рукопожатие нельзя ещё и потому, что наш `ReceiveLoopAsync`
   в этот момент уже держит `ReceiveAsync` на том же сокете.
   **Мой гвард первой печати это пропустил**: он искал `.Wait()` с пустыми скобками.
   Причина моя, третий раз на одном месте.
2. **Единственный кросс-поточный `lock (_mainThread)`.** Главный поток держал его
   *во время вызова действий* (`DrainMainThreadQueue`), а фоновый (`SetState` →
   `StateChanged` → `Enqueue`) ждал тот же монитор. Любая задержка внутри действия
   (включая пункт 1) превращается в клинч: главный ждёт сокет, фоновый ждёт монитор.
3. **Неограниченный дренаж** `while (_mainThread.Count > 0)` без единого лога —
   потенциальный livelock, который выглядит ровно как «редактор мёртв, в Console тишина».

**Что сделано (печать 2):**

* `socket.Abort()` вместо `CloseAsync().Wait(1s)` — **ноль** блокирующих вызовов во
  всех 11 `.cs` (гвард теперь ищет `.Wait(` с любыми аргументами, а также
  `Task.WaitAll/WaitAny`, `.Join(`, `Monitor.Enter`, `Thread.Sleep`,
  `.GetAwaiter().GetResult()`);
* `Queue<Action>` + `lock` → **`ConcurrentQueue<Action>`**: кросс-поточных блокировок
  в клиенте не осталось вовсе, действия вызываются вне любого монитора;
* потолок дренажа `MaxActionsPerFrame = 512` + красная строка про livelock (с остатком очереди);
* **фазовые логи рукопожатия h0…h9** с **тегом потока** (`main` / `ФОНОВЫЙ n (main=m)`):
  h0 Connect · h1 состояние · h2 hello+ready в очереди · h3 hello сервера ·
  h4 EnsureBodyOnConnect вход · h5 persona_request в очереди · h6 watchdog заведён ·
  **h7a получен JSON, разбираю MiniJson** · h7 кадр взят в обработку ·
  h8 вокруг `VrmLoader.Swap` (до/после) · h9 канарейка;
* **канарейка главного потока** (h9): раз в 0.5 с печатает «главный поток ЖИВ» +
  состояние, счётчики принятых кадров, длину очереди действий, `IncomingPending`,
  `OutgoingPending`, персону, `_personaFrameSeen` и статус тела. Работает до конца
  рукопожатия или 30 с, затем сама выключается. Это прибор, а не косметика:
  **канарейка молчит = главный поток заблокирован** (а последняя hN называет место),
  **канарейка идёт, а счётчики не растут = встал транспорт**;
* `IncomingPending`/`OutgoingPending` в транспорте; сброс дедупликации
  `persona_request` при обрыве (`Disconnected`/`Failed`), чтобы reconnect снова попросил кадр;
* в оверлей добавлен счётчик принятых кадров.

**Карта фаз рукопожатия** (что означает и где искать, если это последняя строка):

| Фаза | Строка | Если замерла здесь |

**Чего я НЕ утверждаю.** Точный механизм Б/В из песочницы не подтверждён: Unity здесь
нет, а плавающая точка замера означает гонку. Поэтому печать 2 — это (а) устранение
**всех** блокирующих конструкций, найденных чтением кода, и (б) приборы, которые на
следующем замере назовут строку. Если замер Г зависнет снова, hN + канарейка дают
однозначный ответ, и это будет уже не гипотеза.

**Остаточная гипотеза (не исключена, проверяется замером Г):** зависание внутри
`MiniJson.Deserialize` на кадре `persona` (крупный вложенный JSON: `card`, `voice`,
`face.window`, `face.idle`, оверрайды) — именно поэтому h7a ставится **до** разбора.
Все циклы парсера, которые я прочитала, индекс продвигают, но доказать это без
запуска нельзя. Если замер Г покажет `h7a` последней строкой — это оно, и я перепишу
разбор на конечный автомат с явным счётчиком шагов.
